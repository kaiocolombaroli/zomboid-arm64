# Project Zomboid ARM64: M5 — plano de implementação

**Goal:** Ter som no jogo em ARM64, ligando a integração macOS às DLLs oficiais FMOD ARM64.

**Architecture:** `fmodintegration64.dll` deixa de ser stub e vira ponte para `libfmodintegration.dylib`. As importações `FMOD_*` são resolvidas nas DLLs oficiais, e as de C++ passam por um shim para a API C. A camada Darwin ganha `pthread`, `dispatch` e demais funções.

**Tech Stack:** C/C++ com llvm-mingw, Python 3, Java 25 ARM64, FMOD Engine 2.03.x ARM64.

**Spec:** `docs/design/specs/2026-11-05-zomboid-arm64-som-design.md`

## Global Constraints

- Jogo: `C:\Program Files (x86)\Steam\steamapps\common\ProjectZomboid`. Nada é escrito nessa pasta.
- Versão do jogo: FMOD 2.3.9.
- As DLLs FMOD ficam em `third-party/fmod/` e `dist/`, fora do git.
- CTest: `tools\toolchain\cmake\cmake-4.4.5-windows-arm64\bin\ctest.exe --test-dir build --output-on-failure`.
- Todo binário em `dist/` deve ser `arm64`.
- `launcher/run-game.ps1` mantém `-NoSound`, e som fica ligado por padrão ao fim do plano.
- Sem commit até o usuário pedir. Sem navegador. Fluxo: Sonnet implementa, Haiku valida, Opus decide.
- Conta, senha e termos do FMOD são do usuário.

## Review Focus

1. **`pthread_cond_timedwait` com tempo no passado:** deve retornar `ETIMEDOUT` sem travar. Teste na Tarefa 2.
2. **Mutex destruído e recriado:** o mesmo endereço não pode herdar estado antigo. Teste na Tarefa 2.
3. **Thread do FMOD chamando Java:** o callback deve anexar a thread uma única vez. Teste na Tarefa 3.
4. **DLL FMOD x64 em `dist/`:** o launcher deve recusar. Teste na Tarefa 4.
5. **Fechar o jogo com som tocando:** o processo deve terminar. Teste na Tarefa 4.

### Tarefa 3: Ponte FMOD

**Files:**
- Create: `native/fmodshim/fmodshim.c`, `tools/gen_fmod_shim.py`, `tests/harness/FmodHarness.java`
- Modify: `native/CMakeLists.txt`, `native/loader/macho_loader.c`, `native/bridge/bridge_main.c`, `tests/harness/run-native.ps1`

**Interfaces:**
- Produces: `dist/fmodintegration64.dll`.
- Produces: `void* dw_fmod_resolve(const char* apple_name);`, chamado pelo loader em dependências `@rpath/libfmod*.dylib`.

- [ ] **Step 1: Classificar as 70 importações C++**

Separar nomes que a própria dylib resolve (`_ZGV`, `EventInstanceCallback`) dos métodos `FMOD::*`. Cada método vira chamada à função C equivalente, com tabela revisada à mão.

- [ ] **Step 2: Escrever o harness**

`FmodHarness`: inicializa com `javafmod`, como `FMODManager`, carrega `Master` e um banco real de `media/sound/banks`, cria uma instância de evento, toca por 2 s, confere `FMOD_Studio_EventInstance_GetPlaybackState`, registra callback, para e libera. Imprime resultados de cada chamada.

- [ ] **Step 3: Implementar**

O loader aceita as dependências `@rpath/libfmod.dylib` e `libfmodstudio.dylib`, e encaminha ao shim, sem carregá-las. O harness usa saída `NOSOUND_NRT` para ser determinístico, e depois a saída real.

- [ ] **Step 4: Comparar com o x64**

Run: `run-native.ps1 -Lib fmod -Arch x64`, depois `-Arch arm64`, e `compare.py`.
Expected: mesmas sequências de resultados e estados.

- [ ] **Step 5: Ouvir**

O harness em saída real toca um evento audível, e o usuário confirma.

**Pare e reporte se:** a integração usar estrutura com layout divergente do Windows, ou a mesma falha resistir a 3 tentativas.
